## Arquitectura y límites

- Grafana `13.2.4`, Prometheus `3.15.1`, Blackbox `0.29.1`; k6 `grafana/k6:1.0.0`.
- El receptor se habilita con `--web.enable-remote-write-receiver`; destino k6:
  `http://prometheus:9090/api/v1/write`. No es un bloque `remote_write:` de envío en `prometheus.yml`.
- Prometheus pertenece solo a `uce-observability_monitoring`. Conserva volumen, 384 MiB, 0,50 CPU,
  retención de 24 h y 256 MB de bloques. WAL/head ocupan espacio adicional.
- Solo Grafana publica `127.0.0.1:3000`. No se publica 9090 ni 5665; no se instala Cloud ni otro servicio.
- El complemento `tests/load/compose.prometheus.yaml` añade la red externa `uce-observability_monitoring`
  al k6 original, conservando `ecommerce-net` → `ecommerce-uce_ecommerce-net` mediante merge.
  Sin `--prometheus` no se incorpora ese complemento ni se necesita observabilidad.
- El smoke usa otro Compose independiente: redes externas de aplicación y observabilidad, sin credenciales,
  socket Docker, data-net ni puertos. Límite propio de 256 MiB y 0,25 CPU.
- Las redes son bridges con `internal=false`: el aislamiento se basa en las conexiones y en no publicar puertos.
  No se presenta como una barrera frente al administrador del host o a contenedores de la misma red.

Cambiar los argumentos exige **recrear únicamente Prometheus**. No basta SIGHUP ni un simple restart.
No usar `down`, `--force-recreate` del stack entero ni eliminar volúmenes. Habrá un hueco breve de
observabilidad; no debe ocultarse ni interpretarse como caída de la tienda. Grafana detecta el JSON nuevo
por polling cada 30 s; no requiere reiniciar Grafana ni cambiar la fuente `uce-prometheus`.

Verificar el flag efectivo mediante lectura:

# These are real benchmark runs: they scale product-service and generate load.

Sin `--prometheus` se mantienen escenarios, carga y umbrales anteriores. El runner completo sigue escalando
réplicas y recogiendo logs/estadísticas; browse/purchase/mixed preparan datos de negocio. La configuración
de credenciales de esos escenarios sigue en el Compose original; no se copia a métricas ni dashboards.
La lectura heredada del puerto se difiere hasta `main()`: importar el runner o pedir `--help` no lee `.env`.
Las consultas `docker inspect` del runner seleccionan solo los campos necesarios, no el entorno completo.

Remote Write usa histogramas nativos, envíos cada 5 s y stale markers al finalizar. No se activan histogramas
mediante el flag antiguo de Prometheus; no hace falta para el receptor 3.15.1. Se desactiva el informe de uso
de k6 en este modo. La recepción efectiva de la imagen k6 existente quedó comprobada en el primer smoke.

Etiquetas globales: `testid = run_id`, `load_scenario`, `product_replicas`, `measurement_kind=benchmark`
y `comparison_key`. `scenario` sigue identificando el ejecutor k6; `phase` conserva prep/main/warmup/sustained/ramp.
Los system tags se limitan a status, method, name, group, check, error_code, scenario y expected_response.
No se exportan URL completa, identificadores de usuario/pedido/petición, VU ni iteración como etiquetas.

`RUN_ID` y `RESULTS_DIR` están reservados. En modo Remote Write también se reservan sus opciones de salida,
etiquetas y formato. Se rechazan variables repetidas. La reserva exclusiva de nombres evita colisiones entre
ejecuciones concurrentes. Cada k6 escribe primero en `results/.pending/<run_id>/`; solo un resumen con identidad
correcta se copia, sin cambiar sus bytes, a `<run_id>.json`. Un fallo de setup que produzca `unknown.json`
queda aislado, nunca sobrescribe otro resultado. No borrar esa evidencia al diagnosticar un fallo.

Se conservan resumen, log, contexto y código de salida k6, incluido 99. El comportamiento de salida del runner
no se cambia: el código k6 queda en `k6_exit_code`; no debe inferirse del éxito del proceso Python.
`summary_status` informa si el resumen se verificó. El contexto Remote Write añade fechas UTC/epoch, etiquetas,
configuración, hashes de los scripts y digests de imágenes de aplicación; no cambia los archivos históricos.

`observability.export_status` distingue `samples_observed`, `incomplete` y `unverified`. Consulta en Prometheus
la presencia real de VUs, contador HTTP e histogramas para ese testid. `samples_observed` **no prueba entrega
sin pérdidas**, ni que los umbrales hayan pasado; un k6 exit 0 tampoco prueba recepción.

## Dashboard y precisión

Abrir [UCE — Pruebas de carga k6](http://127.0.0.1:3000/d/uce-k6).
Seleccionar tipo de medición, escenario, réplicas, testid, fase y endpoint. Un testid a la vez evita sumar
pruebas distintas. La tabla conserva la identificación real del rango aunque la ejecución ya haya terminado.

- VUs: gauge real; no se distribuye artificialmente por fase.
- RPS: tasa del contador HTTP, ventana de 30 s, agrupada por fase.
- p95: `histogram_quantile(0.95, sum(rate(...[30s])))` de histogramas nativos. Se agregan distribuciones,
  no percentiles. La duración exportada está en segundos; se multiplica por 1000 para mostrar milisegundos.
- Errores: tasa de solicitudes `expected_response=false` / tasa total, por 100. Respeta la clasificación
  de respuestas esperadas de los escenarios, incluida la excepción de 429 durante login.
- Un numerador ausente solo se toma como cero si hay un denominador observado positivo; sin tráfico
  suficiente no se presenta 0 %. Si cualquier serie HTTP observada tiene menos de dos muestras en la ventana,
  se omite ese cálculo: el primer error aislado no se oculta como cero ni se suma una tasa parcial.
  No se aplica rate() a los gauges de porcentaje k6.
- Las series de actividad requieren VUs con antigüedad de hasta 15 s. Sin muestras suficientes se muestra
  **Sin datos**; las líneas no unen huecos. Sin actividad reciente no se distingue automáticamente entre
  una prueba terminada y una interrupción del envío.
- La última muestra es el timestamp registrado por k6, no una medición independiente del instante de
  llegada al servidor. La antigüedad puede seguir creciendo para una ejecución histórica dentro del rango.

Los percentiles temporales estimados no son equivalentes exactos a los finales del JSON. Los umbrales
siguen evaluándose por k6 en sus unidades originales. No convertir una línea de referencia en un veredicto.
Grafana no importa los JSON antiguos ni fabrica puntos de aquellas ejecuciones. Las series nuevas duran
según la retención de Prometheus; los informes JSON permanecen como evidencia agregada independiente.
Las sondas Blackbox y el monitor de consola son fuentes distintas del tráfico de k6. Cerrar la consola reduce
sus consultas, pero Blackbox mantiene sus propias sondas; registrar estas condiciones en una comparación.

## Smoke · primera ejecución completada; repetición requiere autorización

Requiere el receptor ya aplicado y ambos stacks sanos. No usar `run_load.py` para este ensayo: escalaría
réplicas. El smoke independiente hace exactamente ocho GET a `/api/products?limit=1` con un VU, sleep 5 s,

La primera ejecución y sus archivos están en [SMOKE_K6_20261024.md](SMOKE_K6_20261024.md).
Procedimiento de referencia desde la raíz, solo para una nueva autorización explícita:

```powershell
$smoke = @(
  '--project-name', 'uce-k6-smoke',
  '--env-file', 'tests/demo/observability/compose.vars',
  '--project-directory', 'tests/demo/observability',
  '-f', 'tests/demo/observability/compose.k6-smoke.yaml'
)
$smokeId = 'smoke-' + (Get-Date -Format 'yyyyMMdd-HHmmss') + '-' + [guid]::NewGuid().ToString('N')
$replicaNames = @(docker ps --filter 'label=com.docker.compose.project=ecommerce-uce' `
  --filter 'label=com.docker.compose.service=product-service' --filter 'status=running' --format '{{.Names}}')
$replicas = $replicaNames.Count
if ($replicas -lt 1) { throw 'No running product-service replica was observed.' }
$outDir = Join-Path (Get-Location) 'tests/load/results/smoke'
New-Item -ItemType Directory -Path $outDir -Force | Out-Null
if ((Test-Path (Join-Path $outDir "$smokeId.json")) -or (Test-Path (Join-Path $outDir "$smokeId.log"))) {
  throw 'Run id collision; choose another id.'
}
docker compose @smoke config --quiet
# This command generates eight real catalogue requests. Run only after authorization:
docker compose @smoke run --rm --no-deps `
  -e "RUN_ID=$smokeId" `
  -e K6_PROMETHEUS_RW_SERVER_URL=http://prometheus:9090/api/v1/write `
  -e K6_PROMETHEUS_RW_TREND_AS_NATIVE_HISTOGRAM=true `
  -e K6_PROMETHEUS_RW_PUSH_INTERVAL=5s `
  -e K6_PROMETHEUS_RW_STALE_MARKERS=true `
  k6-smoke run --out experimental-prometheus-rw `
  --system-tags status,method,name,group,check,error_code,scenario,expected_response `
  --tag "testid=$smokeId" --tag load_scenario=integration_smoke `
  --tag "product_replicas=$replicas" --tag measurement_kind=integration_smoke `
  /scripts/smoke_prometheus.js 2>&1 | Tee-Object -FilePath (Join-Path $outDir "$smokeId.log")
$smokeExit = $LASTEXITCODE
"k6 exit: $smokeExit; testid: $smokeId"
```

Abrir Grafana con `measurement_kind=integration_smoke`, escenario integration_smoke y el testid mostrado.
Comprobar: resumen con `http_reqs.count=8`, umbrales/checks cumplidos, ausencia de errores de envío,
etiquetas reales, VUs, contador HTTP y muestras de tipo histograma nativo en Prometheus. Confirmar que las
series dejan de aparentar actividad tras finalizar y que la tienda y la Etapa A siguen sanas. Registrar el
código k6, versiones, hora, réplicas y resultados en VALIDACION_K6.md; el exit 0 solo no basta.
Los archivos quedan bajo `results/smoke/`, fuera del glob de históricos benchmark. No son una medición
de capacidad ni una comparación 1/3. No ejecutar simultáneamente con un benchmark académico.
